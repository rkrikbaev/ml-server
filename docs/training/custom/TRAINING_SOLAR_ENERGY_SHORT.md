# SOLAR ENERGY: Логика обучения модели прогноза генерации СЭС

Цель документа: зафиксировать практическую логику обучения модели для прогноза генерации электроэнергии солнечной электростанции на базе уже поддержанных типов моделей `prophet` и `xgb`.

Документ описывает именно training-логику и критерии выбора модели. Он не заменяет общие документы пайплайна, а уточняет их для кейса solar generation.

---

## 1. Что прогнозируем

Целевой ряд:
- активная генерация СЭС (`P_WATT`, `power`, `active_power` или эквивалент);
- шаг ряда обычно `15m`, `30m` или `1h`;
- прогноз строится на горизонт `output_range`, заданный runtime/train-конфигом.

Особенности домена:
- ночью генерация близка к нулю;
- внутри дня есть выраженный профиль по солнцу;
- облачность, температура, сезон и угол солнца сильно влияют на амплитуду;
- возможны ограничения сверху по установленной мощности станции и куртейлмент;
- у ряда часто есть длинные участки нуля, которые являются нормой, а не пропуском.

Практический вывод:
- для solar generation недостаточно смотреть только на autoregression;
- нужно явно учитывать календарную сезонность и желательно weather/context features;
- метрики надо интерпретировать отдельно для daylight и для полного ряда.

---

## 2. Когда использовать `prophet`, а когда `xgb`

### 2.1 Prophet

Предпочтителен, если:
- нужен быстрый baseline;
- ряд в основном объясняется сезонностью и календарем;
- есть ограниченный набор внешних признаков;
- важна интерпретируемость тренда и сезонных компонент;
- нужно быстро получить устойчивый результат на умеренно чистом временном ряде.

Сильные стороны для СЭС:
- хорошо моделирует дневную/недельную/годовую сезонность;
- удобен как базовый solar-profile model;
- дает понятную decomposition-логику.

Ограничения:
- хуже работает при сильной зависимости от погоды, если внешние регрессоры заданы слабо;
- сам по себе не учитывает нелинейные взаимодействия так же гибко, как `xgb`.

### 2.2 XGBoost (`xgb`)

Предпочтителен, если:
- есть weather-признаки и календарные признаки;
- нужно ловить нелинейные зависимости;
- есть достаточно длинная история и приемлемое качество данных;
- важен более точный operational forecast на горизонте от нескольких шагов до суток.

Сильные стороны для СЭС:
- хорошо использует лаги, rolling statistics и weather features;
- обычно лучше baseline-моделей на переменной облачности;
- легко масштабируется на richer feature set.

Ограничения:
- требует аккуратной feature engineering;
- сильнее чувствителен к leakage и к качеству train/validation split;
- без корректных признаков может переобучаться на погодные и календарные шумы.

## 3. Входной контракт для обучения

Минимальный набор для solar training:
- временная колонка `timestamp`;
- целевая колонка генерации `y`;
- частота ряда `freq`;
- идентификатор объекта (`object_reference`, `station_id` или аналог);
- train-параметры модели.

Желательный набор дополнительных признаков:
- `temperature`;
- `cloud_cover`;
- `irradiance` / `ghi` / `dni` / `dhi`, если доступны;
- `wind_speed`;
- `humidity`;
- календарные признаки: час, день года, месяц, weekday;
- признаки daylight: sunrise/sunset, is_daylight;
- station metadata: installed_capacity_mw, orientation/tilt, если доступны.

Если weather недоступен:
- `prophet` остается допустимым baseline;
- `xgb` должен компенсировать отсутствие погоды более сильными календарными и lag-признаками, но точность обычно ниже.

## 4. Подготовка данных именно для СЭС

### 4.1 Базовая очистка

До обучения обязательно:
1. привести временную колонку к единой timezone policy;
2. отсортировать ряд по времени;
3. удалить дубликаты timestamps;
4. отделить реальные пропуски от нормальных ночных нулей;
5. проверить отрицательные значения генерации.

Рекомендуемое правило:
- отрицательная генерация для СЭС обычно либо ошибка измерения, либо служебный режим;
- в train-пайплайне такие точки либо клипуются к `0`, либо исключаются по явному правилу качества.

### 4.2 Нули ночью

Ночные нули не должны считаться аномалией.

Практика:
- если `is_daylight == 0`, нулевые значения допустимы;
- если `is_daylight == 1`, длинные серии нулей нужно дополнительно проверять как возможный outage, curtailment или sensor fault.

### 4.3 Ограничение сверху

Для СЭС полезно контролировать ceiling:
- если известна установленная мощность, проверять что генерация не превышает realistic upper bound;
- явные выбросы выше физически возможной мощности лучше удалять или клиповать до допустимого максимума.

### 4.4 Train/validation/test split

Только time-based split:
- train — ранняя часть ряда;
- validation — следующий непрерывный интервал;
- test — последний непрерывный интервал.

Нельзя:
- случайно перемешивать timestamps;
- использовать random split, который ломает временную структуру.

Для solar forecasting особенно важно, чтобы в validation/test попадали полные суточные циклы.

## 5. Общая схема обучения

```text
Исторические данные СЭС
  -> quality checks
  -> очистка и нормализация
  -> daylight-aware preprocessing
  -> train/val/test split
  -> линейная регрессия (обязательный baseline)
  -> ветка prophet или xgb
  -> валидационный прогноз
  -> метрики (сравнить все три модели)
  -> выбор candidate
  -> публикация artifacts в MLflow
```

> **Требование:** Всегда обучайте линейную регрессию (Ridge) как базовую модель. Prophet/XGBoost должны стабильно превосходить её хотя бы по одной метрике. Baseline также логируется в MLflow с тегом `model_type=linear_baseline`.

Рекомендуемый общий output candidate training:

```json
{
  "model_name": "prophet|xgb",
  "status": "success|error",
  "fit_time_sec": 0.0,
  "metrics": {
    "mae": 0.0,
    "mape": 0.0,
    "rmse": 0.0
  },
  "train_params": {"...": "..."},
  "notes": "solar-specific remarks"
}
```

## 6. Ветка обучения `prophet` для СЭС

### 6.1 Когда эта ветка особенно полезна

`prophet` хорошо подходит как:
- baseline для новой станции;
- интерпретируемая первая модель;
- fallback-кандидат, если weather-признаки неполные;
- модель для случаев, где доминирует устойчивая сезонность.

### 6.2 Подготовка датасета

Для `prophet` нужен DataFrame с колонками:
- `ds` — timestamp;
- `y` — генерация.

Дополнительно можно добавлять regressors:
- `cloud_cover`;
- `temperature`;
- `irradiance`;
- `is_daylight`;
- `month` или season markers.

Практическое правило для solar:
- если нет внешних regressors, модель все равно можно обучить только на `ds/y`;
- если regressors есть, нужно гарантировать их наличие и в train, и в future/predict pipeline.

### 6.3 Типовая логика fit

1. Создать `Prophet` с параметрами из `train_params`.
2. Включить нужные seasonalities.
3. При наличии weather/context features зарегистрировать их как additional regressors.
4. Выполнить `fit(train_df)`.
5. Построить future frame на validation/test horizon.
6. Выполнить `predict(future_df)`.
7. Сравнить `yhat` с фактическими значениями.

Пример train-параметров:
- `changepoint_prior_scale`;
- `seasonality_prior_scale`;
- `seasonality_mode`;
- `yearly_seasonality`;
- `weekly_seasonality`;
- `daily_seasonality`.

### 6.4 Solar-specific рекомендации для Prophet

- `daily_seasonality` часто полезна, потому что профиль генерации внутри суток критичен;
- `yearly_seasonality` важна из-за сезонного изменения длины дня и высоты солнца;
- `weekly_seasonality` включается только если у станции реально есть недельный operational pattern;
- `seasonality_mode="multiplicative"` часто полезен, когда амплитуда сезона зависит от уровня ряда;
- если ночью много нулей, имеет смысл проверить качество fit отдельно по daylight subset.

### 6.5 Ограничения Prophet для solar forecasting

- при быстро меняющейся облачности без weather regressors ошибка может резко расти;
- при сильных нелинейных эффектах модель обычно проигрывает `xgb`;
- если outages и curtailment не размечены, Prophet может попытаться считать их сезонностью.

## 7. Ветка обучения `xgb` для СЭС

### 7.1 Когда эта ветка особенно полезна

`xgb` обычно основной кандидат, если:
- доступны погодные признаки;
- требуется operational accuracy;
- есть достаточно истории для построения лагов и статистик;
- важны нелинейные взаимодействия между погодой, временем суток и прошлой генерацией.

### 7.2 Feature engineering для solar generation

Минимальный набор признаков:
- лаги генерации: `y_lag_1`, `y_lag_2`, `y_lag_step_day`, `y_lag_step_week`;
- rolling statistics: mean/std/min/max на окнах 3, 6, 12, 24 шагов;
- календарные признаки: hour, weekday, month, dayofyear;
- daylight признаки: `is_daylight`, `sun_elevation_proxy` или sin/cos hour encoding.

Желательный набор:
- `cloud_cover`;
- `temperature`;
- `irradiance` или proxy на основе weather;
- взаимодействия weather x daylight.

Для циклических признаков желательно использовать:
- `sin_hour`, `cos_hour`;
- `sin_dayofyear`, `cos_dayofyear`.

### 7.3 Типовая логика fit

1. Построить feature matrix из исторического ряда и внешних признаков.
2. Удалить строки, где лаги еще не определены.
3. Разделить данные на train/validation/test по времени.
4. Создать `XGBRegressor` с train-параметрами.
5. Выполнить fit на train.
6. Получить прогноз на validation/test.
7. Сравнить с фактами и зафиксировать метрики.

Пример train-параметров:
- `n_estimators`;
- `max_depth`;
- `learning_rate`;
- `subsample`;
- `colsample_bytree`;
- `min_child_weight`;
- `reg_alpha` / `reg_lambda`.

### 7.4 Solar-specific рекомендации для XGB

- используйте признаки прошлого дня и прошлой недели, потому что генерация СЭС сильно повторяет солнечный цикл;
- обязательно контролируйте leakage: weather и target-derived features должны быть доступны на момент прогноза;
- при multi-step horizon лучше явно определить strategy: recursive, direct или block prediction;
- для operational day-ahead прогноза важно, чтобы weather features соответствовали forecast horizon, а не факту из будущего.

### 7.5 Ограничения XGB для solar forecasting

- без хороших weather features преимущество над Prophet может быть небольшим;
- на маленьких датасетах и при большом числе признаков легко получить переобучение;
- feature pipeline должен быть полностью воспроизводим в inference runtime.

## 8. Метрики качества для СЭС

Минимально считать:
- `MAE`;
- `MAPE`;
- `RMSE`.

Для solar forecasting рекомендуется дополнять интерпретацию:
- отдельно считать метрики на всем ряде;
- отдельно считать метрики только на daylight-интервалах;
- отдельно смотреть ошибки на пиковых часах генерации.

Причина:
- ночные нули могут искусственно улучшать общую картину;
- operationally важнее качество прогноза именно тогда, когда станция реально генерирует.

Практический критерий выбора winner-model:
1. сначала смотреть daylight quality;
2. потом устойчивость на полном test-интервале;
3. потом сложность и воспроизводимость inference pipeline.

## 9. Рекомендуемая стратегия выбора между `prophet` и `xgb`

### 9.1 Минимальный practical workflow

1. Подготовить единый clean dataset для СЭС.
2. Обучить линейную регрессию (Ridge) как интерпретируемый baseline.
3. Обучить `prophet`.
4. Построить признаки и обучить `xgb`.
5. Сравнить все три модели на одном и том же validation/test окне.
6. Выбрать winner по daylight metrics и operational stability.
   Prophet/XGBoost допустимы в production только если превосходят linear baseline.

### 9.2 Простая матрица выбора

| Условие | Предпочтение |
|---|---|
| Нет погодных признаков, нужен baseline | `prophet` |
| Есть погодные признаки и длинная история | `xgb` |
| Важна объяснимость сезонности | `prophet` |
| Важна максимальная точность на переменной облачности | `xgb` |
| Нужен fallback без сложной feature engineering | `prophet` |

## 10. Что должно попасть в MLflow artifacts

Для обеих моделей в Stage 5 рекомендуется сохранять:
- обученный model artifact в `bundle/model`;
- runtime config в `bundle/configuration/cache_config.json`;
- train/validation/test snapshots при необходимости воспроизводимости;
- summary метрик;
- список использованных признаков для `xgb`;
- список registered regressors для `prophet`.

Для solar case особенно полезно логировать:
- долю daylight samples;
- наличие/отсутствие weather features;
- installed capacity, если она участвует в нормализации;
- train period и season coverage.

## 12. Критерий готовности solar training pipeline

- данные очищены с учетом специфики СЭС;
- ночные нули не трактуются как дефект данных;
- `prophet` и `xgb` обучаются на одном и том же временном разбиении;
- рассчитаны как минимум `MAE`, `MAPE`, `RMSE`;
- daylight quality оценена отдельно;
- выбран winner-model или зафиксировано, что `prophet` остается baseline, а `xgb` требует доработки признаков;
- artifacts и runtime config готовы к публикации в MLflow.

---

## 13. Короткая рекомендация по умолчанию

Для новой СЭС без богатого набора погодных признаков:
- начать с `prophet` как устойчивого baseline.

Для СЭС с доступными weather features и задачей повысить точность:
- делать основной production candidate на `xgb`, а `prophet` держать как baseline/fallback для сравнения качества и деградации.
